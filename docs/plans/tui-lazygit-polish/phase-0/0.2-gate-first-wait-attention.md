# 0.2 — Gate first-wait attention

**Phase:** 0 · Happy path  
**Status:** Proposed  
**Visual change:** Yes  
**Risk:** Low–Medium (focus policy; must not fight ADR “gates are non-blocking”)  
**Primary surfaces:** `internal/tui/monitor` (focus, gate overlay, footer status)

## Problem

Gates intentionally do **not** steal focus on every arrival (non-blocking
regions). That is right for power users mid-scroll, but the **first** wait of a
run is easy to miss: status lives in a dim footer line while Steps/Transcript
still look “active.”

## Goal

Make a pending gate impossible to miss **without** freezing navigation:

1. Soft attention chrome on the gate strip
2. Auto-focus gate on the *first* wait after entering a run (already partially
   covered by `FocusPendingInput` — harden and make visual)
3. Footer status for waiting states uses the Marker/Error emphasis and reads as
   the primary signal

## Decisions to lock

1. **First wait:** entering Monitor (new or resume) with a pending gate focuses
   Gate. Subsequent arrivals while the operator is in Steps/Transcript do **not**
   steal focus (keep ADR).
2. **Visual nudge without focus steal:** when a gate is pending and focus ≠ Gate,
   render gate chrome with warning border / title prefix `GATE · needs input`
   even while blurred, and prepend `tab gate` in the footer compact hints.
3. **No animation dependency:** prefer static emphasis (border token, title
   badge, status word). Optional blink is out of scope for v1 of this item.
4. **Queue depth:** show `(N pending)` in both gate title and status when
   `len(inputQueue) > 1` (already partially present — make consistent).

## Implementation sketch

- Audit `FocusPendingInput`, `focusInputOnArrival`, and gate-arrival event
  paths; document the single “first wait” rule in one place.
- Gate overlay / panel title: pending + unfocused → warning-styled border or
  `needs input` badge via shared theme tokens (no ad-hoc hex).
- Status label already branches on gate kind — ensure waiting strings win visual
  weight over “running” when any gate is pending.
- Tests: enter run with pending review → focusGate; second question while
  reading transcript → focus unchanged + footer still advertises `tab gate`.

## Acceptance

- [ ] New/resumed run with pending gate opens focused on Gate
- [ ] Later gate while focused on Transcript does not yank focus
- [ ] Unfocused pending gate still shows distinct “needs attention” chrome
- [ ] Footer status never says only `running` when a gate is pending
- [ ] Multi-entry queue shows count in title and status

│   plan      ✓ done           ││ …                             │

  awaiting review · 1-9 decision · enter open · esc blur · ? more

```text
╭─ ab12cd34 · feature › Steps ─╮╭─ [TRANSCRIPT] implement · LIVE ─╮

│ ▌ implement ● running        ││ ▸ Tool Grep TestFlatten        │

╰───────────────────────────────────────────────────────────────╯
  awaiting answer (2 pending) · tab gate · j/k scroll · ? more
```
