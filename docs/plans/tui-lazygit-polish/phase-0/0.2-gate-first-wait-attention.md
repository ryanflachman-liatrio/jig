# 0.2 — Gate first-wait attention

**Phase:** 0 · Happy path  
**Status:** Decisions locked — see [../../DECISIONS.md](../../DECISIONS.md)  
**Visual change:** Yes  
**Risk:** Low–Medium (focus policy; must not fight ADR 0002)  
**Depends on:** 0.1 (stable enter/resume), 0.4 (leave), 0.3 (footer status)  
**Primary surfaces:** `internal/tui/monitor` (focus, gate overlay, footer status)

## Problem

Gates intentionally do **not** steal focus on every arrival (ADR 0002). That is
right for power users mid-scroll, but the **first** wait of a run is easy to
miss. Worse: today `FocusPendingInput` / `focusInputOnArrival` is consumed only
by `PromptRequest` — first `ReviewRequest` / `InputRequest` / `AgentQuestion` /
etc. after an empty enter never auto-focuses.

## Goal

Make a pending gate impossible to miss **without** freezing navigation:

1. Soft attention chrome on the gate strip (title/status; not a second primary border)
2. Auto-focus gate on the *first* wait after entering a run — **all gate kinds**
3. Footer/status for waiting states reads as the primary signal

## Locked decisions

| ID | Lock |
|---|---|
| A5 | First wait after enter/resume focuses Gate for **any** kind; later arrivals do not steal |
| C3 | Focused: `[GATE] · awaiting review` · Blurred pending: `GATE · needs input` |
| E1 | Blurred pending: **title/status only**; border stays Iron |
| D6 | Rules cover **all** gate kinds, not review-only |
| G4 | Status step field prefers pending gate’s step (when 1.1 lands) |

## Implementation sketch

- Audit `FocusPendingInput`, `focusInputOnArrival`, and every gate-arrival path
  in `monitor_events.go`; consume `focusInputOnArrival` for all kinds once.
- Document the single “first wait” rule next to ADR 0002 / FocusPendingInput.
- Gate title: pending + focused → `[GATE] · …`; pending + blurred →
  `GATE · needs input` (Iron border).
- Status/footer: waiting strings win visual weight over “running” when any gate
  is pending (0.3 status segment).
- Queue depth: `(N pending)` in title and status when `len(inputQueue) > 1`.
- Tests: enter with pending review → focusGate; enter empty then first
  ReviewRequest → focusGate; second question while reading transcript → focus
  unchanged + footer still advertises `tab gate`.

## Acceptance

- [ ] New/resumed run with pending gate (any kind) opens focused on Gate
- [ ] Enter empty, then first Review/Input/Question/Prompt/Recovery/…
      auto-focuses Gate once
- [ ] Later gate while focused on Transcript does not yank focus
- [ ] Unfocused pending gate shows `GATE · needs input` (Iron border)
- [ ] Focused gate shows `[GATE] · …` (Charple border)
- [ ] Footer/status never says only `running` when a gate is pending
- [ ] Multi-entry queue shows count in title and status
