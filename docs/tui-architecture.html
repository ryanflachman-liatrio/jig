02 Screen state machine

Four values of the screen enum root.go:19-24. Solid arrows go forward, dashed arrows go back, the amber arrow is the shortcut that skips a screen. Click a node for its model, keys and render strategy.

ctrl+c → tea.Quit from any screen root.go:108. It is the only key the root itself handles.

The monitor is a nested state machine. An explicit monitorMode monitor.go:21-30 — modeList (step list, j/k move a selection cursor) and modeChat (one step's transcript, j/k scroll) — sits inside the Monitor screen, wrapped in two modal overlays. The four-tier key precedence is load-bearing, and the reason the mode is explicit rather than inferred is written into the type's own doc comment: it "keeps the list-navigation keymap from colliding with the viewport's scroll keymap."
  1. pendingPrompt != nil → every key goes to the textarea; ctrl+s submits monitor.go:186-210
  2. pendingReview != nil → digits 1–9 pick a verdict, esc/q leaves; everything else is swallowed by a bare return m, nil so navigation is frozen while a gate is up monitor.go:214-234
  3. switch m.mode — modeList claims j/k/enter/esc monitor.go:239-277; modeChat claims only esc/h/←, tab/shift+tab, enter/space and o monitor.go:278-326
  4. everything unclaimed falls through to m.vp.Update(msg) monitor.go:336 — which in modeChat is the whole point: j/k/ctrl+d/pgdn reach the viewport's own keymap untouched

Tier 3 must come before tier 4 or the viewport eats j/k before the list ever sees them — and note the two modes make opposite choices about the same keys, which is exactly why an implicit mode wouldn't have worked. Both human-input events also force m.mode = modeList on arrival monitor.go:387,412: a gate must never render behind a drilled-in chat view, or its keys would be ambiguous. monitor_test.go pins all of this, including that j does not move the list cursor in modeChat or during a review.

Navigation is state-preserving. showMonitorMsg only rebuilds the monitor when the run ID actually differs root.go:162, and seeds the fresh one from run.Snapshot() root.go:166-169. Combined with the root fanning every engine event to both runs and monitor regardless of which screen is active root.go:124-128, monitor state survives navigating away and back.

04 Engine event bus

This is the most important diagram on the page. Eleven event types event.go:9-121 leave the engine by two different paths with opposite durability guarantees. Understanding which path an event takes tells you whether you can trust it.

scheduler.emit() durable

Scheduler goroutine only. Journal write is synchronous and happens before any subscriber sees the event.
  • s.seq++monotonic per run engine.go:1096
  • MarshalEnvelope(seq, e){seq, ts, kind, data} journal.go:54
  • manifest.Writer.AppendLine→ journal.jsonl, plus result.json on terminal StepStatus engine.go:1112
  • fanOut(s.subs, e)may drop engine.go:1115

The invariant this buys you: in-memory TUI state is always a subset of fold(journal.jsonl). A dropped event is recoverable by replay.

reporter.ev() lossy

Worker goroutines. Bypasses emit entirely — tags run/step IDs and fans out without touching scheduler state or any lock.
  • Output / ToolCall / Messagecalled by the executor from its own goroutine engine.go:232-236
  • closure tags RunID, StepIDpre-bound at dispatch engine.go:570-586
  • fanOut(subs, e)no journal, no seq, droppable engine.go:1141

Deliberately lock-free because it runs off the scheduler goroutine. The cost: these events are unrecoverable if dropped — which is exactly why bulk content must not ride this path.

fanOut drops on a full channel — by design

A non-blocking select with a bare default. The scheduler must never block on a slow UI, so the UI is allowed to miss events. Subscriber channels are 256-deep engine.go:112; the TUI drains exactly one per Bubble Tea update cycle, so a burst can and will overflow.

// fanOut sends e to each subscriber channel, dropping events for slow consumers.
// Called from both scheduler and reporter (which runs in worker goroutines).
func fanOut(subs []chan<- Event, e Event) {
	for _, ch := range subs {
		select {
		case ch <- e:
		default:          // ← the drop
		}
	}
}

The eleven events, and who actually listens

Seven are consumed by the TUI. Four are not — and three of those four carry information the user would want.

EventPathJournal kindTUI consumer
Gate failures, loop iterations and engine errors are invisible in the UI. GateResult, LoopFired and RunError are emitted and journaled but no TUI branch handles them — verified: rg 'GateResult|LoopFired|RunError' internal/tui returns nothing. A gate can reject a step, a bounded loop can burn all its iterations, and a worktree creation failure can abort the run, all without a word on screen beyond the resulting status change.
PromptRequest breaks journal replay. It is the one event type missing from both eventKind journal.go:26-51 and decoders journal.go:70-111. It therefore serialises as {"kind":"unknown"}, and UnmarshalEnvelope hard-errors with unknown event kind "unknown" on that line journal.go:120-122. Confirmed on disk in existing runs under .jig/runs/. Any future journal-replay monitor — the obvious way to open a run from a previous process — dies on the first workflow that asks the user a question. Two lines fix it.

06 Concurrency map

Goroutine census for one live run. The design's backbone is a single-writer invariant: one scheduler goroutine owns every piece of mutable run state, with no mutex protecting it. Everything else is a channel message.

Bubble Tea loop ×1

Event loop + renderer. Owns rootModel. All Update and View calls happen here.

tea.Cmd goroutines ×n

One per in-flight command — including waitForEngineEventCmd, which is permanently parked on a channel receive. root.go:235

scheduler ×1 per run

Sole owner of states, worktrees, diffs, pendingUserInputs, seq. No mutex. engine.go:104,240

step workers ×n ≤ max_parallel

One per dispatched step; calls Executor.Execute then posts stepDoneMsg back to the inbox. engine.go:606-609

SDK subprocess reader ×n

Inside each AgentExecutor, feeding client.ReceiveMessages(ctx). agent.go:57

signal.NotifyContext ×1

Interrupt / SIGTERM watcher established in main. main.go:25

Three deliberate consequences

Manager.mu guards almost nothing

It protects only the runs map and the subs slice engine.go:27-33. It is the single mutex in the package. All workflow state is owned by a goroutine instead of guarded by a lock.

Gates run synchronously on the scheduler

runGate engine.go:757 is called inline from handle, not dispatched to a worker. It blocks the whole run — accepted deliberately, to preserve single-writer.

Snapshot() can't deadlock on a dead scheduler

A fast path reads finalSnap lock-free once done is observed closed; onDone writes it before the close, satisfying the memory-model happens-before engine.go:99-102,160-181. Both selects also guard on done in case the scheduler exits mid-request.

Events are processed strictly in order

Exactly one waitForEngineEventCmd is outstanding at a time — armed in Init, re-armed on every delivery root.go:99-102,128. Serial by construction, at the cost of one event per update cycle.

Three consequences that are arguably bugs

Elapsed times freeze. There is no tea.Tick anywhere in the TUI (verified: rg 'tea.Tick' internal/tui → nothing), but stepDuration calls time.Now() for any step without an end time monitor.go:948-958. The number therefore only advances when some other event happens to arrive — during a long silent agent step the duration visibly stops moving. A one-second ticker while !m.done fixes it.
Late subscribers never join a running run. Start snapshots the subscriber list at launch engine.go:73-76 and hands that copy to the scheduler. Anyone calling Subscribe() afterwards sees nothing from runs already in flight. There is also no unsubscribe, so channels accumulate for the process lifetime.
Runs from a previous process are unopenable. rootModel.handles is only populated when this process starts a run root.go:195. A run directory sitting in .jig/runs/ from an earlier session has no *engine.Run, so showMonitorMsg finds nothing to snapshot and the monitor opens empty. Rehydrating from journal.jsonl is the intended fix — and is what the PromptRequest journal gap above would break.

07 Disk layout & phase status

Two append-only JSONL files with different jobs: the journal records what happened to the run; the transcript records what the agent said.

│   ├── journal.jsonl                   JournalPath()     datastore.go:54

│   ├── steps/<step-id>/                StepDir()         datastore.go:45
│   │   ├── result.json                 ResultPath()      datastore.go:57

root == "" is the documented opt-out from all persistence datastore.go:29 — used by tests, and by Manager.Start, where an uncreatable root is deliberately non-fatal: the run still works, it just doesn't persist engine.go:78-90. That same nil-check cascades into StepRequest.TranscriptPath, so persistence-off means transcript-off too.

Why the transcript exists

The bus carries liveness; the file carries content. Because fanOut drops on a full channel, no event may be the only copy of something the user needs. So StepMessage event.go:60-65 is a four-field nudge — run, step, seq, iteration — and the actual message lands in transcript.jsonl first. A dropped StepMessage only means "the view is one seq stale," self-correcting on the next read. StepToolCall is now marked Deprecated for precisely this reason event.go:41-46: it tried to put content on the bus.

Writer — append-only, resumable

  • Create resumes seq from the existing line count, so retries and loop iterations append rather than truncate writer.go:40
  • Append stamps v/seq/ts and clamps each block to 256 KiB on a rune boundary, setting Truncated writer.go:64,107
  • flushes on every append so a concurrent reader only ever sees whole lines
  • every entry tagged with iter and attempt so loop iterations sharing one file stay distinguishable executor.go:30-33

Reader — handle-free

  • Count / Window(offset,limit) / Tail(n) each open, read to EOF, and close — no long-lived handle to invalidate reader.go:34-64
  • silently skips malformed or partial trailing lines, so reading a file mid-write is safe reader.go:83
  • preserves unknown block types, so an SDK addition never breaks an old reader transcript.go:16
