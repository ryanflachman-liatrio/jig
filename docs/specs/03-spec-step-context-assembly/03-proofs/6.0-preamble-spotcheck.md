# Proof 6.6 — behavioral spot-check: old skill prose vs. new engine preamble

> **This is a manual human review, not an automated assertion.** Spec Unit 6 is
> explicit that behavior-preservation is a human spot-check, not an equivalence
> gate. This document assembles the concrete before/after so a reviewer can judge
> whether the `plan` agent's *orientation* is preserved once the hand-authored
> narration is replaced by the engine-assembled preamble.

## What was compared

For the `plan` step of `examples/feature.toml`:

- **Old (removed) prose** — the position/loop narration that used to live in
  `.agents/skills/plan/SKILL.md` (see `6.0-skill-narration-removed.txt` for the
  full diff).
- **New preamble** — the engine-assembled "Workflow context" block the `plan`
  agent now receives, prepended ahead of the (trimmed) skill body. This is the
  committed golden `2.0-plan-preamble.txt`, regenerated from the real example
  after Task 6.2 added the `[step.context]` blocks.

### Old prose (removed)

```
You ... receive research findings from two parallel research agents (backend and
frontend/TUI) and turn them into a concrete, ordered implementation plan.

## Your inputs
2. Backend research (@research_backend.summary) — findings on engine, ...
3. Frontend research (@research_frontend.summary) — findings on TUI, ...
4. Reviewer feedback (@plan_review) — present only when the human rejected a
   previous plan iteration. ...

### approach — ... This is what the `implement` agent reads to understand intent. ...
### summary — ... This is what the human reads in the `plan_review` gate.
```

### New engine-assembled preamble (first run)

```
## Workflow context

You are step `plan` in workflow `feature`.
Purpose: turn research into an ordered, reviewable implementation plan
Notes: cross-check every file path and type name before emitting a task

Upstream (already complete):
- `research_backend` (succeeded) — surface backend findings (engine, storage, schema) that shape the plan
- `research_frontend` (succeeded)
- `security_scan` (succeeded)
These reach you as the inputs listed below; this section is orientation only.

Downstream (what your output feeds):
- `plan_review` (human review) — a person reviews your `summary`
- `implement` (agent) — consumes your `tasks`, `approach` (conditional on `plan_review == 'approve'`)

---
```

On a `plan_review == 'revise'` re-run the preamble additionally carries
`(iteration 2 of 3)` and a `State:` line naming the reviewer's revision request
(see `3.0-revise-loop-preamble.txt`).

## Orientation mapping (old fact → where it now lives)

| Orientation the old prose gave the agent | Where it appears in the new preamble |
| --- | --- |
| "you receive research from two parallel research agents" | `Upstream (already complete):` lists `research_backend`, `research_frontend` (and `security_scan`) — more complete than the prose, and with real dispatch statuses. |
| backend/frontend research are your inputs | Upstream block + the `@ref` inputs still delivered below the preamble (framing-only guarantee: bodies arrive via `@ref`, not the preamble). |
| "reviewer feedback present only when the human rejected a previous iteration" | The `State:` line on a revise re-run names exactly that, and only then — the engine knows the run state, so the conditional narration is no longer guessed by the skill. |
| "`approach` is what the `implement` agent reads" | `Downstream:` `- implement (agent) — consumes your tasks, approach`. |
| "`summary` is what the human reads in the `plan_review` gate" | `Downstream:` `- plan_review (human review) — a person reviews your summary`. |

Two facts the preamble adds that the prose never had: the **security_scan**
upstream (the prose omitted it) and the **conditional** on the `implement` edge
(`plan_review == 'approve'`). Author intent that is *not* graph-derivable is
preserved via `[step.context]` (`Purpose`/`Notes` lines).

## Preliminary assessment

Every orientation fact the old prose conveyed is present in the new preamble, and
the preamble is strictly more accurate (real statuses, the omitted upstream, the
guard). The skill body retains all *how-to-do-the-job* guidance (task rules, risk
levels, "verify file paths before emitting a task"). No orientation gap is
apparent from the deterministic comparison.
