internal/workflow · code-guided tour

Inside a jig workflow

A workflow starts as author-friendly TOML and ends as a validated, execution-ready graph. This guide explains the objects that carry that graph, the transformations performed by the loader, and the invariants guaranteed before the engine sees it.

TOML→ decoded structs→ resolved assets→ expanded modules→ *Workflow
01 · Mental model

A graph with a typed contract

The package does more than deserialize TOML. It compiles an author graph into an execution graph, resolves external authoring assets, applies configuration layers, and rejects ambiguous or unsafe combinations. The engine can therefore treat the result as a stable contract rather than raw configuration.

structure

The graph

Step.ID names nodes. DependsOn creates DAG edges. Conditions and routes add typed decisions and bounded back-edges.

data

The contracts

Input, OutputType, Schema, check artifacts, and review targets describe what moves between nodes.

policy

The guardrails

Defaults, profiles, retry rules, isolation, budgets, security, and validation determine how each node may execute.

The key boundary internal/workflow knows the schema and proves the graph is coherent. It does not execute agents or schedule the graph.

03 · The central type

Step is a validated union

Go stores every step kind in one large struct. The discriminator is Step.Type; validation makes the union safe by requiring each kind's fields and rejecting fields belonging to other kinds.

TypePurposeDefining fieldsImportant constraints
agent Runs a fresh agent context. skill or agent_file, inputs, tools, model, schema, context Exactly one prompt source; backend/transport must be valid; isolation is resolved.
command Runs deterministic shell work. run or script Exactly one command source; agent/check/review-only fields are rejected.
check Runs a typed quality gate. run/script, applies_when, findings Produces pass/fail/skip/error semantics and must define automatic remediation routes.
review Pauses for a human decision. review[] source/file targets Targets must be unambiguous, resolvable, and connected to dependencies.
subworkflow Invokes a reusable module. module, with Author-facing only; replaced before the engine receives the graph.
common fields

Graph and execution

ID, DependsOn, When, Output, OutputType, failure policy, timeout, retry, idempotence, resource class, mutation paths, secrets, deterministic validation, routes, and step security.

resolved fields

What TOML does not show

The loader computes effective context injection and isolation, resolves prompt/template bodies, snapshots those bodies, parses file schemas, and fills inherited configuration.

06 · Transformations

The loading pipeline

Loading is deliberately ordered. Each phase produces information the next phase needs—for example, file-derived tools must exist before isolation is defaulted, and schemas must resolve before field references are checked.

Acquire root source

Load reads the file and computes its absolute path and directory. Decode already has the TOML string. DecodeLocked first validates and indexes persisted module sources.

Decode TOML

BurntSushi TOML fills a zero-value Workflow. Four types interpret richer author syntax themselves:

  • Duration parses Go duration strings.
  • Input accepts reference strings or inline tables.
  • OutputType accepts a scalar kind or enum table.
  • Schema converts nested tables into sorted field trees.

Reject unknown keys

MetaData.Undecoded() turns misspelled or unsupported keys into an immediate parse error. Custom-unmarshaled subtrees count as consumed.

Resolve authoring assets

In order: skill instructions, agent files, output templates, and literal review sources. Resolved prompt and template text is copied into snapshot fields immediately.

Load and apply profiles

Built-ins are combined with project profiles from .agents/jig/profiles/*.toml. Profile values fill fields still unset after explicit TOML and agent-file resolution.

Apply defaults and build the ID index

Global defaults and built-in fallbacks become concrete step values. Effective context injection, security overrides, backend transport, and isolation are resolved. The step ID index is rebuilt.

Expand modules recursively

If subworkflow nodes exist, the author graph is saved, child workflows are prepared recursively, bindings and exports are type-checked, internal IDs are namespaced, and public references are rewritten.

Resolve schemas and validate

External JSON Schemas become the same Schema/Field representation used by inline TOML. All structural, referential, policy, and DAG checks then run and aggregate their errors.

Attach provenance and return

On success, source path and original TOML are attached. The caller receives a fully resolved *Workflow. On any failure, no partially valid workflow is returned.

07 · Resolution rules

Configuration precedence

The first non-zero value wins, from strongest author intent to weakest fallback.

StepExplicit [[step]] fields
Agent fileTools and model from frontmatter
ProfileReusable named configuration
DefaultsWorkflow-wide configuration
Built-inHard-coded final fallback

Why pointer booleans exist

*bool preserves three states: unset, explicitly true, and explicitly false. This matters for inject_context and security overrides.

The additive exception

AskUserQuestion from @interactive is added to allowed tools even when a step already declared its own allowlist.

Backend fallback

The backend falls back to Claude. Cursor and Codex select ACP when transport is omitted; Claude selects SDK.

Isolation fallback

An agent with a mutating allowed tool defaults to worktree. Everything else defaults to none.

input boundary

Bindings

Every required module input must be supplied through with. Bindings may be paths, upstream fields, check artifacts, parent-module inputs, or sibling-module exports. Their declared types must agree.

output boundary

Exports

Exports resolve to real internal producers. Parent inputs, conditions, review targets, and feedback references are rewritten to those producers.

graph boundary

Roots and terminals

Parent dependencies and invocation guards flow into module roots. Consumers of the module wait for all internal terminal steps.

reproducibility

Provenance

Each module's absolute path, source TOML, and SHA-256 are captured. Locked decoding refuses missing or checksum-mismatched module sources.

09 · Proof before execution

Validation closes the graph

The validator accumulates problems, sorts them, and returns one ValidationError. This lets authors fix a set of related problems in one pass.

Metadata and budgetsRequired name/version, non-empty graph, non-negative budgets, valid capacity limits.
IdentityEvery step ID is present, well formed, and unique.
Step unionEach type has its required fields and no incompatible fields.
ReferencesDependencies exist; inputs also declare ordering; fields and artifacts exist.
Output contractsScalar and structured shapes do not conflict; reserved base fields cannot be redeclared.
Execution policyRetry needs idempotence, backoff is coherent, mutation paths and secrets are names.
Conditions and routesGuards are typed, targets exist, branches are explicit, and loop counts are bounded.
DAG integrityDFS rejects dependency cycles. Legal route back-edges are deliberately outside the DAG check.

Details worth remembering

Why are schema files resolved during validation?

Cross-step references need every producer's field tree. Resolving files first lets inline and external schemas share the same downstream checking path.

Why must an input reference also appear in depends_on?

The data edge and scheduling edge must agree. Otherwise a consumer could ask for output from a producer it does not wait for.

Why are route cycles allowed but dependency cycles rejected?

depends_on defines the static DAG. Routes are separately validated bounded back-edges with explicit iteration limits, preserving termination.

Why does structural-only decoding skip files?

Tests and editor tooling can validate object shape without requiring the author's filesystem. File-backed details remain unresolved rather than being guessed.

10 · Handoff

What the engine receives

Resolved

  • Defaults and profiles folded into steps
  • Backend, transport, context, and isolation concrete
  • Prompt and template bodies snapshotted
  • JSON Schema files parsed into field trees
  • Modules expanded and references rewritten

Proven

  • Step kinds are internally consistent
  • References and types line up
  • Retries and loops are bounded
  • The dependency graph is acyclic
  • Source and module provenance is available
Compact mental model The loader behaves like a small compiler: decode syntax → resolve symbols and assets → inline modules → type-check references → emit an execution graph.
